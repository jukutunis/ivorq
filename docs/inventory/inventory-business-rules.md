# Inventory Module — Business Rules

## Stock Movement Rules

### BR-001 — No Negative Stock
No movement (issue, transfer out, adjustment out) may reduce a stock balance below zero. The service validates the current balance before any deduction. Attempting to issue or transfer more than the on-hand quantity raises a `ValidationException`.

### BR-002 — Movement Atomicity
All balance updates are wrapped in a `DB::transaction()`. If any part of a multi-line operation fails, the entire operation rolls back. No partial stock movements are permitted.

### BR-003 — Quantity Must Be Positive
All movement quantities must be > 0. Zero or negative quantity values are rejected at the Form Request validation layer.

### BR-004 — Decimal Quantities
All quantities are stored as `decimal(10, 3)` to support both integer units (PCS, BOX) and fractional units (KG, LITER). The UI displays quantities truncated to relevant decimal places based on unit type.

### BR-005 — Stock Card Created for Every Movement
Every stock balance change creates at least one stock card entry. The StockMovementService is the only place that writes to `inventory_stock_cards`. No direct model writes to this table are permitted outside the service.

### BR-006 — Stock Card Immutability
Stock card entries are never updated or deleted. There is no `updated_by`, no `softDeletes`, and no `updated_at` usage after creation. A mistake is corrected by posting a new corrective movement (adjustment), never by editing the original entry.

### BR-007 — Balance Synchronization
After every movement, `inventory_stock_balances.quantity` is updated atomically in the same transaction. The balance record's `status` column is recomputed after each update:
- `out_of_stock` if quantity = 0
- `low_stock` if 0 < quantity < item.reorder_point
- `in_stock` if quantity >= item.reorder_point

### BR-008 — Balance Record Auto-Creation
When a movement is posted for an item+location combination that has no balance record, the record is created with `quantity = 0` before the movement is applied. This means opening_balance movements are the correct way to initialize stock.

## Item Management Rules

### BR-010 — Item Code Auto-Generation
Item codes are generated by the controller using the `ITM-%05d` pattern, scoped per property:
```php
$seq = InventoryItem::where('property_id', $propertyId)->withTrashed()->count() + 1;
$itemCode = sprintf('ITM-%05d', $seq);
```
This mirrors the PMS `GST-%05d` / `RES-%05d` pattern.

### BR-011 — Unique SKU
If a SKU is provided, it must be unique within the property. Null SKUs are permitted (multiple items can have no SKU).

### BR-012 — Deactivation Does Not Remove Stock
Deactivating an item (`is_active = false`) does not alter stock balances or delete stock card entries. The item becomes ineligible for new receipts, issues, or transfers. Historical records are preserved. The balance is still visible in reports.

### BR-013 — Category and Unit Cannot Be Deleted if Referenced
A category or unit cannot be deleted (soft or hard) if any active item references it. The service returns a `ValidationException` with a clear message.

### BR-014 — Min Stock ≤ Reorder Point
`min_stock` must be ≤ `reorder_point`. The form request validates this relationship. (Rationale: reorder should happen before stock drops to the minimum threshold.)

### BR-015 — Max Stock Optional
`max_stock` is optional. When set, it serves as a UI guideline for ordering decisions. The system does not enforce it as a hard cap.

## Transfer Rules

### BR-020 — From and To Must Differ
A transfer cannot have the same `from_location_id` and `to_location_id`. Validated at the Form Request layer.

### BR-021 — Transfer Lines Required to Submit
A transfer must have at least one line to be submitted. Submitting an empty transfer raises a `ValidationException`.

### BR-022 — No Stock Change Until Completion
Stock is only deducted from the source and added to the destination when the transfer is **Completed**. Submitting does not reserve or hold stock.

### BR-023 — Stock Validated at Completion Time
When completing a transfer, the service validates that sufficient stock exists at `from_location` for each line item at that moment. If any line cannot be fulfilled, the entire completion is rejected (BR-002 atomicity).

### BR-024 — Transfer Cancellation
A transfer may be cancelled from `Draft` or `Submitted` status. Once `Completed`, it cannot be cancelled. Reversal requires a new transfer in the opposite direction.

### BR-025 — Auto-Generate Stock Cards on Completion
Completing a transfer creates exactly two stock card entries per line:
- `transfer_out` at `from_location` (quantity_change = -qty)
- `transfer_in` at `to_location` (quantity_change = +qty)
Both entries reference `reference_type = 'transfer'` and `reference_id = transfer.id`.

### BR-026 — Transfer Status Machine

| From | Allowed Transitions |
|------|-------------------|
| Draft | Submitted, Cancelled |
| Submitted | Completed, Cancelled |
| Completed | (terminal) |
| Cancelled | (terminal) |

## Adjustment Rules

### BR-030 — Reason Required
All adjustments require a reason text. This is enforced at the Form Request layer.

### BR-031 — System Quantities Frozen at Draft Creation
When a draft adjustment is created, the system quantity for each line is captured from the current balance at that moment. This snapshot is stored in `quantity_system` and is read-only for the life of the adjustment.

### BR-032 — Variance Computation
`quantity_variance = quantity_actual - quantity_system`. This is computed and stored, not derived at read time, to preserve the audit record.

### BR-033 — Zero-Variance Lines Skip Stock Card
If `quantity_variance = 0` for a line, no stock card entry is created for that line. The adjustment is still recorded.

### BR-034 — Approval Required Before Stock Changes
No stock change occurs when an adjustment is submitted. Stock only changes when the adjustment is **Approved**. This requires the `inventory.approve` permission.

### BR-035 — Stock Validated at Approval Time (Negative Variance)
If a line has a negative variance, the service validates that the current balance ≥ |variance| before approval, since stock may have changed since the draft was created. The approval fails if this check is not met.

### BR-036 — Adjustment Status Machine

| From | Allowed Transitions |
|------|-------------------|
| Draft | Submitted, Cancelled |
| Submitted | Approved, Rejected |
| Approved | (terminal) |
| Rejected | (terminal) |
| Cancelled | (terminal) |

## Opening Balance Rules

### BR-040 — Opening Balance is a Special Movement
Loading initial stock for a new property or location uses a dedicated `opening_balance` movement type. It is posted through the same StockMovementService as all other movements.

### BR-041 — Opening Balance Can Only Be Posted to Zero-Balance
An opening balance movement can only be posted if the current balance is 0. This prevents accidentally doubling stock on an already-initialized item.

## Audit Rules

### BR-050 — All Transactions Carry posted_by
Every stock card entry records `posted_by` (the authenticated user's ID). This is required, non-nullable.

### BR-051 — Adjustment Approval Stamped
When an adjustment is approved, `approved_by` and `approved_at` are recorded on the adjustment header.

### BR-052 — Transfer Completion Stamped
When a transfer is completed, `completed_by` and `completed_at` are recorded on the transfer header.

### BR-053 — Stock Card Includes Reference
When a movement is generated by a transfer or adjustment, the stock card entry records:
- `reference_type` — `'transfer'` or `'adjustment'`
- `reference_id` — the ULID of the parent record

This allows tracing any stock card entry back to its source document.

## Property Isolation Rules

### BR-060 — All Records Are Property-Scoped
Every table in the Inventory module includes a `property_id` column. The `BelongsToProperty` trait is applied to all models. The global scope ensures queries never return records from other properties.

### BR-061 — Cross-Property Operations Prohibited
Transfers only occur between locations within the same property. The Form Request validates that both `from_location` and `to_location` belong to the current property.

### BR-062 — Items, Categories, and Units Are Property-Local
Category and unit records are created per property. There is no global/shared master data in V1. Two properties may have identically named categories that are entirely independent records.
