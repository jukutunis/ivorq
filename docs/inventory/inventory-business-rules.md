# Inventory Module — Business Rules
# Version 1.1

## Stock Movement Rules

### BR-001 — No Negative Stock
No movement (issue, transfer out, adjustment out) may reduce a stock balance below zero. The service validates the current balance before any deduction. Attempting to issue or transfer more than the on-hand quantity raises a `ValidationException`. This validation is applied per line before any writes begin (see BR-002).

### BR-002 — Movement Atomicity
All balance updates are wrapped in a `DB::transaction()`. If any part of a multi-line operation fails, the entire operation rolls back. No partial stock movements are permitted.

### BR-003 — Quantity Must Be Positive
All movement quantities must be > 0. Zero or negative quantity values are rejected at the Form Request validation layer.

### BR-004 — Decimal Quantities
All quantities are stored as `decimal(10, 3)` to support both integer units (PCS, BOX) and fractional units (KG, LITER). The UI displays quantities without trailing zeros for integer-type units.

### BR-005 — Stock Card Created for Every Movement
Every stock balance change creates exactly one stock card entry per item+location combination. The `StockMovementService` is the only place that writes to `inventory_stock_cards`. No direct model writes to this table are permitted outside the service.

### BR-006 — Stock Card Immutability
Stock card entries are never updated or deleted. There is no `updated_by`, no `softDeletes`, and no `updated_at` after creation. A mistake is corrected by posting a new corrective movement (adjustment), not by editing the original entry.

### BR-007 — Balance Synchronization
After every movement, `inventory_stock_balances.quantity` is updated atomically within the same transaction. The `status` column is recomputed after each update:
- `out_of_stock` — quantity = 0
- `low_stock` — 0 < quantity < `item.reorder_point`
- `in_stock` — quantity >= `item.reorder_point`

### BR-008 — Balance Record Auto-Creation
When a movement is posted for an item+location combination that has no balance record, the record is created with `quantity = 0` before the movement is applied.

## Item Management Rules

### BR-010 — Item Code Auto-Generation
Item codes are generated by the controller using the `ITM-%05d` pattern, scoped per property:
```php
$seq = InventoryItem::where('property_id', $propertyId)->withTrashed()->count() + 1;
$itemCode = sprintf('ITM-%05d', $seq);
```

### BR-011 — Unique SKU
If a SKU is provided, it must be unique within the property. Null SKUs are permitted (multiple items may have no SKU).

### BR-012 — Deactivation Does Not Remove Stock
Deactivating an item (`is_active = false`) does not alter stock balances or delete stock card entries. The item becomes ineligible for new receipts, issues, or transfers. Historical records and balances are preserved.

### BR-013 — Category and Unit Cannot Be Deleted if Referenced
A category or unit cannot be deleted (soft or hard) if any active item references it. The service returns a `ValidationException` with a clear message.

### BR-014 — Min Stock ≤ Reorder Point
`min_stock` must be ≤ `reorder_point`. Validated at the Form Request layer.

### BR-015 — Max Stock Optional
`max_stock` is optional. When set, it serves as a UI guideline only. The system does not enforce it as a hard cap on receipts.

## Costing Rules

### BR-016 — Average Cost is Item-Level
`inventory_items.average_cost` represents the current weighted average cost per unit for the item, computed across all locations. It is a property-level figure, not per-location. All quantities for an item (regardless of location) participate in the WAC calculation.

### BR-017 — Weighted Average Cost on Receipt
When a receipt is **posted**, the item's `average_cost` is updated using the Weighted Average Cost (WAC) formula for each item that appears in the receipt:

```
new_avg_cost = (qty_on_hand * current_avg_cost + Σ(line.quantity * line.unit_cost))
               ÷ (qty_on_hand + Σ(line.quantity))
```

Where:
- `qty_on_hand` = sum of `quantity` across all `inventory_stock_balances` for this item (all locations), read within the transaction using `lockForUpdate()`
- `Σ(line.quantity * line.unit_cost)` = sum across all receipt lines for this item in this receipt (handles multiple lines per item)
- `Σ(line.quantity)` = total quantity received for this item across all lines

**Edge case — zero on-hand:** When `qty_on_hand = 0`, `new_avg_cost = Σ(line.quantity * line.unit_cost) / Σ(line.quantity)` (the receipt unit cost directly).

The `average_cost` update occurs within the same `DB::transaction()` as the stock balance update for atomicity.

### BR-018 — Issue Stamps Average Cost at Post Time
When an issue is **posted**, the current `item.average_cost` is read (within the transaction) and stamped onto each stock card entry as `unit_cost`. The `total_value` on the stock card = `|quantity_change| * unit_cost`. This value is immutable once written (BR-006 applies).

The issue service does **not** change `item.average_cost` — only receipts update it.

### BR-019 — Unit Cost is Nullable for Non-Costed Movements
For `transfer_out`, `transfer_in`, and `opening_balance` movements, `unit_cost` and `total_value` on the stock card are `null`. These movement types do not carry cost tracking in V1.

For `adjustment_in` and `adjustment_out`, `unit_cost = item.average_cost` at time of approval and `total_value` is populated. This allows cost impact reporting on adjustments even though `average_cost` is not changed.

### BR-020 — Average Cost Precision
`average_cost` is stored as `decimal(14,4)` to support high-value items (e.g., spare parts, specialised chemicals) and to avoid rounding errors in WAC accumulation over many receipts.

## Receipt Rules

### BR-030 — Receipt Workflow
A receipt follows a two-step lifecycle:

| Status | Stock Change | Editable |
|--------|-------------|----------|
| Draft | None | Yes |
| Posted | Applied | No |
| Cancelled | None | No (terminal) |

Status machine: Draft → Posted \| Cancelled

### BR-031 — Receipt Lines Required to Post
A receipt must have at least one line before it can be posted. Attempting to post an empty receipt raises a `ValidationException`.

### BR-032 — Receipt Posting Applies Stock and Cost Atomically
Posting a receipt triggers, within a single `DB::transaction()`:
1. For each line: validate quantity > 0
2. For each line: create `purchase_receipt` stock card entry (with `unit_cost`, `total_value`)
3. For each line: update balance at `line.location_id`
4. For each unique item in the receipt: recalculate and save `item.average_cost` via WAC (BR-017)
5. Update receipt: `status = posted`, set `posted_by`, `posted_at`, `received_at` (if not set, defaults to `posted_at`)

### BR-033 — Receipt Cancellation
A receipt may only be cancelled from `Draft` status. A `Posted` receipt cannot be cancelled. Errors in a posted receipt are corrected via an Adjustment (BR-070 area).

### BR-034 — Receipt Line Location Must Belong to Current Property
The `location_id` on each receipt line must reference an active location belonging to the same property. Validated by the Form Request using a property-scoped `Rule::exists`.

## Issue Rules

### BR-040 — Issue Workflow
An issue follows the same two-step lifecycle as a receipt:

| Status | Stock Change | Editable |
|--------|-------------|----------|
| Draft | None | Yes |
| Posted | Applied | No |
| Cancelled | None | No (terminal) |

Status machine: Draft → Posted \| Cancelled

### BR-041 — Issue Lines Required to Post
An issue must have at least one line before it can be posted. Attempting to post an empty issue raises a `ValidationException`.

### BR-042 — Issue Posting Validates and Applies Stock Atomically
Posting an issue triggers, within a single `DB::transaction()`:
1. For each line: validate quantity > 0
2. For each line: validate sufficient balance at `line.location_id` (BR-001 — no negative)
3. If ALL lines pass: for each line:
   a. Create `issue` stock card entry with `unit_cost = item.average_cost`, `total_value = quantity * unit_cost`
   b. Deduct balance at `line.location_id`
4. Update issue: `status = posted`, set `posted_by`, `posted_at`, `issued_at` (defaults to `posted_at`)

All line validations happen before any writes (step 1-2 before step 3), ensuring atomicity (BR-002).

### BR-043 — Issue Cancellation
An issue may only be cancelled from `Draft` status. A `Posted` issue cannot be cancelled or reversed directly. Errors are corrected via a Return movement or Adjustment.

### BR-044 — Department Tracking
`department_id` on the issue header is nullable in V1. When provided, it must reference a department belonging to the current property. Populated at creation time, not required.

### BR-045 — Polymorphic Reference is V1-Nullable
`issued_to_type` and `issued_to_id` are optional in V1 for manual issues. These fields are reserved for V2 integration (Engineering Work Orders, Housekeeping Tasks, PMS Folios). When provided, no FK enforcement exists at the DB level (polymorphic relationship); the service layer validates the reference if needed.

## Transfer Rules

### BR-050 — From and To Must Differ
A transfer cannot have the same `from_location_id` and `to_location_id`. Validated at the Form Request layer.

### BR-051 — Transfer Lines Required to Submit
A transfer must have at least one line to be submitted. Submitting an empty transfer raises a `ValidationException`.

### BR-052 — No Stock Change Until Completion
Stock only moves when the transfer is **Completed**. Submitting does not reserve or hold stock.

### BR-053 — Stock Validated at Completion Time
When completing a transfer, the service validates that sufficient stock exists at `from_location` for each line at that moment (BR-001). If any line cannot be fulfilled, the entire completion is rejected.

### BR-054 — Transfer Cancellation
A transfer may be cancelled from `Draft` or `Submitted` status. Once `Completed`, it cannot be cancelled. Reversal requires a new transfer in the opposite direction.

### BR-055 — Stock Cards on Completion
Completing a transfer creates two stock card entries per line:
- `transfer_out` at `from_location` (quantity_change = -qty, unit_cost = null)
- `transfer_in` at `to_location` (quantity_change = +qty, unit_cost = null)

Both reference `reference_type = 'transfer'`, `reference_id = transfer.id`. Cost not tracked on transfers (BR-019).

### BR-056 — Transfer Status Machine

| From | Allowed Transitions |
|------|-------------------|
| Draft | Submitted, Cancelled |
| Submitted | Completed, Cancelled |
| Completed | (terminal) |
| Cancelled | (terminal) |

## Adjustment Rules

### BR-060 — Reason Required
All adjustments require a reason text. Enforced at the Form Request layer.

### BR-061 — System Quantities Frozen at Draft Creation
When a draft adjustment is created, the system quantity for each line is captured from the current balance at `adjustment.location_id` and stored in `quantity_system`. This snapshot is read-only for the life of the adjustment.

### BR-062 — Variance Computation
`quantity_variance = quantity_actual - quantity_system`. Stored at draft creation time, not recomputed.

### BR-063 — Zero-Variance Lines Skip Stock Card
If `quantity_variance = 0` for a line, no stock card entry is created for that line.

### BR-064 — Approval Required Before Stock Changes
Stock changes only occur when the adjustment is **Approved** by a user with `inventory.approve`.

### BR-065 — System Quantity Staleness Check on Approval
**v1.1 update.** Before approving, the service validates that every line's `quantity_system` snapshot still matches the current balance at `adjustment.location_id`:

```
current_balance = StockBalance::where(item_id, location_id)->quantity
if current_balance != line.quantity_system → FAIL
```

If **any** line has a stale system quantity (because a receipt, issue, transfer, or other adjustment moved the stock after this draft was created), the **entire approval is rejected** with a `ValidationException` listing the affected items and their current vs. snapshot quantities.

The adjustment remains in `Submitted` status. The approver must inform the submitter to cancel this adjustment and create a new draft with a fresh snapshot.

This rule protects the integrity of stock take results, ensuring approvals are never applied on outdated data.

### BR-066 — Negative Variance Stock Check
If a line has `quantity_variance < 0`, the service validates that the current balance at `adjustment.location_id` >= |`quantity_variance`|. This check occurs after BR-065 passes (it is logically a subset: if quantity_system is current, then current_balance = quantity_system, and the check becomes quantity_system >= |variance|, i.e., quantity_actual >= 0).

### BR-067 — Adjustment Costs Stamped at Approval
When approval writes stock card entries, `unit_cost = item.average_cost` at the time of approval. `average_cost` is not changed by adjustments — only receipts change WAC.

### BR-068 — Adjustment Status Machine

| From | Allowed Transitions |
|------|-------------------|
| Draft | Submitted, Cancelled |
| Submitted | Approved, Rejected |
| Approved | (terminal) |
| Rejected | (terminal) |
| Cancelled | (terminal) |

## Opening Balance Rules

### BR-070 — Opening Balance is a Dedicated Movement Type
Initial stock loading for a new property or location uses `opening_balance` movement type via `StockMovementService`. An optional `unit_cost` may be provided for cost initialization; if omitted, `average_cost` remains 0 and `unit_cost` on the stock card is null.

### BR-071 — Opening Balance Can Only Be Posted to Zero-Balance
An `opening_balance` movement may only be posted if the current balance is 0. This prevents accidental double-loading.

## Audit Rules

### BR-080 — All Stock Card Entries Carry posted_by
Every stock card entry records `posted_by` (authenticated user ID). Required, non-nullable.

### BR-081 — Receipt and Issue Stamped on Posting
When a receipt or issue is posted: `posted_by` and `posted_at` are recorded on the header.

### BR-082 — Adjustment Approval Stamped
When an adjustment is approved: `approved_by` and `approved_at` recorded.

### BR-083 — Transfer Completion Stamped
When a transfer is completed: `completed_by` and `completed_at` recorded.

### BR-084 — Stock Card References Source Document
Every stock card entry includes `reference_type` and `reference_id` linking to the source document (receipt, issue, transfer, adjustment).

---

## Property Isolation Rules

### BR-090 — All Records Are Property-Scoped
Every table includes `property_id`. The `BelongsToProperty` trait and global scope enforce isolation on all model queries.

### BR-091 — Cross-Property Operations Prohibited
Transfers, receipts, and issues may only reference locations and items within the same property. Validated at the Form Request layer.

### BR-092 — Items, Categories, and Units Are Property-Local
No global/shared master data in V1. Category and unit records are per-property.
