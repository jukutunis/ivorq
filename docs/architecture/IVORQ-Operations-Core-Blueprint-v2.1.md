**Document Type:** Master Architecture Blueprint
**Version:** 2.1
**Status:** Pending CTO Approval

## 1. Domain Architecture
The Operations Core functions as the operational nerve center of IVORQ. Functioning entirely separately from the Finance Suite, it handles physical property management, personnel workflows, preventive/reactive engineering, inventory, and external integrations (PMS).

**Module Hierarchy & Ownership:**
- **Foundation Modules:** (Department, Location, Media, Timeline, Checklist, Document Number, Assignment) 
  - Ownership: Core Platform. Zero upward dependencies.
- **Support Modules:** (Inventory, Logbook, Incidents, Contractors, PTW, Visitors, Lost & Found, PMS Gateway, Knowledge Base, Risk Register)
  - Ownership: Operations Management.
- **Execution Modules:** (Asset Management, PM, Work Order, Engineering, Housekeeping, HRIS, CAPEX)
  - Ownership: Departmental Operations.

---

## 2. Foundation Architecture (Expanded)

### 2.1 Universal Document Number Engine
- **Entities:** `DocumentNumberTemplate`, `DocumentSequence`, `DocumentPrefix`, `DocumentRule`.
- **Purpose:** Generates globally unique, sequential IDs for end-user readability (e.g., AST-2026-00001, WO-2026-00001).
- **Concurrency Strategy:** Uses atomic database locks or Redis increments (`INCR`) mapped per `property_id` and `year` to guarantee sequence uniqueness under heavy load without blocking long-running transactions.

### 2.2 Universal Assignment Engine
- **Entities:** `Assignment`, `AssignmentHistory`, `AssignmentGroup`, `EscalationRule`, `AssignmentComment`.
- **Purpose:** Detaches assignment logic from entities. PMs, WOs, Incidents, and Inspections utilize this polymorphically.
- **Business Rules:** Triggers automated notification workflows on reassignment and applies time-based `EscalationRule`s if unresolved.

### 2.3 Media & Attachment Foundation (Revised)
- **Support:** Property/Department isolation, Hierarchical Folders, Versioning, Photo/PDF/Video support, Thumbnailing, Metadata (GPS, Timestamp, Device).
- **Retention:** S3 lifecycles handle automated archival based on legal retention policies.

### 2.4 Activity Timeline Foundation (Revised)
- **Support:** Universal chronological audit logging covering Comments, Mentions, Attachments, Assignments, Status Changes, Approvals, and Digital Signatures.

### 2.5 PMS Gateway Foundation
- **Entities:** `PMSGateway`, `WebhookProcessor`, `ReservationSync`, `RoomStatusSync`, `GuestStatusSync`.
- **Purpose:** Ingests external Property Management System data (Check-In/Out, OOO/OOS) to drive Housekeeping dispatching and suppress Engineering PMs in occupied rooms.
- **Error Recovery:** Idempotent webhooks stored in raw format, retried dynamically upon failure.

## 3. Entity Relationships & Execution Modules

### 3.1 Inventory Foundation
- **Entities:** `Inventory`, `Item`, `ItemCategory`, `StockLocation`, `StockMovement`, `InventoryTransaction`, `InventoryAdjustment`, `InventoryCount`, `ToolTracking`, `ConsumableTracking`.
- **Support:** Depletes seamlessly when utilized by Work Orders or PMs. Tracks specific tool checkouts.

### 3.2 Contractor Management & Permit to Work (PTW)
- **Entities:** `Contractor`, `ContractorCompany`, `ContractorCertification`, `PermitToWork`, `PermitApproval`, `PermitChecklist`.
- **Support:** Controls vendor access, tracks insurance expiration, and locks High-Risk Activities (Hot Work, Confined Space) behind multi-level `PermitApproval` workflows linked directly to WOs.

### 3.3 Visitor Management & Lost & Found
- **Entities:** `Visitor`, `VisitorPass`, `VisitorCheckIn`, `LostItem`, `FoundItem`, `Claim`, `StorageLocation`.
- **Support:** Enforces perimeter security and streamlines housekeeping recovery chains, directly integrating with the PMS Gateway for guest identification.

### 3.4 Knowledge Base & Risk Register
- **Entities:** `KnowledgeArticle`, `Risk`, `RiskAssessment`, `MitigationPlan`, `CorrectiveAction`.
- **Support:** Articles tie directly to Asset QR workflows (providing instant Manuals/SOPs). The Risk Register tracks identified hazards and triggers mitigating Work Orders.

---

## 4. Business Rules
1. **Total Isolation:** Every entity must possess a `property_id` for strict multi-tenant isolation.
2. **Immutable Sequences:** Document numbers, once generated by the engine, are immutable and never reused to prevent audit gaps.
3. **Escalation Primacy:** Overdue Universal Assignments auto-escalate directly to Department Managers.
4. **Approval Blockers:** Work Orders tagged with High-Risk categories cannot transition to `In Progress` without an Approved PTW.

---

## 5. Security Model
- **Roles:** Handled dynamically via HRIS designations.
- **Permission Granularity:** View, Create, Execute, Complete, Approve, Dispose, Override.
- **Audit:** All state changes are immutably written to the Activity Timeline.

---

## 6. Mobile First Strategy
Operations happen in the field, demanding robust offline capabilities.
- **PWA Architecture:** Bypasses app store fragmentation.
- **QR / Barcode / NFC Workflow:** Instant scanning opens PMs, Asset info, or Checklists.
- **Offline Sync & Conflict Resolution:** Implements a strict **"First Sync Wins"** methodology. If Technician B syncs an offline checklist execution after Technician A already completed it, Technician B's local device receives a conflict warning requiring Supervisor Review to overwrite the central record.
- **Hardware Integration:** GPS timestamping on critical safety inspections, device camera attachment handling, and digital signatures on glass.

---

## 7. Performance Model & Scalability Review
**Enterprise Baseline:** 100 Properties, 5,000 Employees, 100,000 Assets, 1,000,000 Attachments, 10,000,000 Timeline Events, 10 Years History.
- **Partitioning:** Implement PostgreSQL native table partitioning on `activity_timelines`, `logbooks`, and `inventory_transactions` by Year/Month.
- **Database Strategy:** ULIDs universally applied to prevent B-Tree fragmentation and table-locking during high-concurrency mobile syncing.
- **Search Engine:** Meilisearch or Elasticsearch cluster explicitly indexing Assets, Articles, and Logbooks.
- **Disaster Recovery:** Continuous replication to cross-region standby. S3 multi-zone storage for Media.

---

## 8. Risk Matrix

| Risk Category | Severity | Mitigation Strategy |
| :--- | :--- | :--- |
| **Offline Sync Conflicts** | Critical | Enforce "First Sync Wins". Store conflicting late-syncs in a quarantine table for supervisor approval to prevent data loss. |
| **Data/Storage Growth** | High | PostgreSQL table partitioning implemented day-one for Timeline and Logs. S3 bucket lifecycles auto-compress old media. |
| **Webhook Floods (PMS)** | High | The PMS Gateway strictly processes webhooks through a highly scaled Redis queue. Rate limits applied dynamically. |
| **Cross-Module Coupling** | Critical | Utilize strictly Event-Driven architecture (Publish/Subscribe) between domains to prevent monolithic spaghetti code. |

## 10. Open Questions
1. **Inventory Valuation:** Should the Operations Inventory foundation support weighted average cost (WAC) calculations natively, or should it defer entirely to Finance for valuation?

## 11. CTO Recommendations
1. **Decoupled Universal Engines:** The Document Number Engine and Universal Assignment Engine must be architected as fully isolated packages. They should have zero knowledge of WOs or PMs, relying purely on Polymorphic relationships.
2. **Prioritize Mobile PWA Frameworking Early:** Establish the offline IndexedDB syncing patterns and conflict resolution interfaces immediately during Phase 2.1. Retrofitting offline sync into existing modules later is exceptionally expensive.
3. **Redis Sequence Generation:** Use Redis `INCR` mapped keys for the Document Number sequence generation to ensure ultra-fast lock-free concurrency, syncing to PostgreSQL asynchronously.
