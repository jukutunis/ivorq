# ADR-036: Inventory Ledger Source Identity, Idempotency, Reversal and Correction

**Status:** Approved
**Date:** 2026-06-22

## Context and Current Repository Evidence

Current inventory operations (Receipt, Issue, Transfer, Adjustment, Stock Opname) utilize `StockMovementService` which persists movements to the `inventory_transactions` table. However, all current workflows pass the **parent document ID** (e.g., `$receipt->id` in `Modules/Operations/Inventory/Services/ReceiptService.php` lines 70-100) down to the ledger append as the `$referenceId`.
This creates a critical limitation: the ledger lacks source-line identity. Furthermore, `inventory_transactions` has no unique composite constraint, exposing the ledger to silent duplicate physical appends if a background job retries after a partial failure.

## Decision

### D-INV-03
We will keep the current `reference_type` and `reference_id` fields for document-level compatibility and backward-compatible UI routing.

For all new ledger behavior, we will introduce:
- `source_document_type`
- `source_document_id`
- `source_line_type`
- `source_line_id`
- `movement_role`
- `idempotency_key`

We will enforce a primary duplicate-protection constraint at the database level:
**`UNIQUE(property_id, idempotency_key)`**

The `idempotency_key` must be deterministic and server-generated from Property, source-line identity, movement role, and an operation/version sequence (where multiple legitimate movements can originate from one line).

### D-INV-04
Inventory Ledger entries are **never edited**.

**Reversal:**
- Creates a new opposite-signed ledger entry.
- Records `reverses_inventory_transaction_id` to link back to the original entry.
- Uses its own dedicated `idempotency_key`.

**Correction:**
- Reverses the original entry (via the Reversal workflow above).
- Creates a new replacement entry.
- May store `corrects_inventory_transaction_id` solely for business intent/auditability.
- Never edits historical rows.

No reversal or correction API is authorized in Slice 0 or Slice 1.
The ADR defines future immutable semantics only.

## Rationale

### Source Document and Line Identity Model
By explicitly separating `source_document_*` and `source_line_*`, the ledger achieves a strict 1:1 mapping with the exact operational line that authorized the movement, enabling deterministic recalculations.

### `movement_role` Semantics
The `movement_role` distinguishes the logical action within a single line (e.g., distinguishing a "Transfer Out" component from a "Transfer In" component generated by the exact same `InventoryTransferLine`).

### `idempotency_key` Generation Contract
The `idempotency_key` is a deterministic, versioned, server-generated canonical identifier. It does not require a hash. Its canonical conceptual shape is:

```text
inv-ledger:v1:
property:{property_id}:
source-document:{source_document_type}:{source_document_id}:
source-line:{source_line_type}:{source_line_id}:
movement-role:{movement_role}:
sequence:{sequence}
```

The exact serialization syntax may evolve only through an explicit future version increment.

### Idempotent Retry and Collision Behavior

Same key + same canonical posting intent:
- return or recognize the existing ledger entry;
- do not append another entry;
- do not update InventoryStock again.

Same key + different canonical posting intent:
- reject as an idempotency collision;
- do not append;
- do not update InventoryStock;
- surface a controlled investigation-required failure.

Canonical posting intent must include at minimum:
- property
- source document identity
- source line identity
- movement role
- sequence
- item
- location
- signed quantity
- unit of measure

### Legacy Null-Key Compatibility

Historical legacy rows may retain null idempotency_key.

Slice 0 must use PostgreSQL-compatible protection that enforces uniqueness only
when idempotency_key is not null, such as a partial unique index.

Future controlled ledger entries must never be posted with null
idempotency_key.

### Prohibition Against Ledger Mutation
Following double-entry accounting principles, physical quantities in a closed or posted state cannot be altered. Corrections must follow explicit compensating mechanisms, preserving an immutable audit trail.

## Operational Examples

- **Receipt:** `source_line_id` = `InventoryReceiptLine->id`
- **Issue:** `source_line_id` = `InventoryIssueLine->id`
- **Transfer Out / Transfer In:** `source_line_id` = `InventoryTransferLine->id`. The `movement_role` is `OUT` for the source location and `IN` for the destination.
- **Adjustment:** `source_line_id` = `InventoryAdjustmentLine->id`
- **Stock Opname:** `source_line_id` = `StockCountLine->id`
- **Reversal:** Follows the Reversal rule, generating a new negative line against the same item/location.
- **Correction:** Reverses the old line, appends the new corrected line.

### Explicit Handling of Receiving Integration
For Receiving (`Modules/Operations/Receiving/Services/InventoryReceiptIntegrationService.php`), a deterministic ledger key can be created directly from the `ReceivingDocumentLine` or `InventoryReceiptLine` identity. Line-level source identity is a mandatory target-state requirement for any future Receiving integration. This ADR does not itself authorize operational Receiving wiring, ReceiptService replacement, dual-write, or receipt lifecycle changes.

The integration will be refactored in a separately approved Receipt integration slice to pass line IDs, abandoning the parent-only `$receipt->id` propagation.

## Explicit Non-Goals
- Cost Ledger logic
- GRNI (Goods Received Not Invoiced)
- Accounts Payable (AP)
- Purchase Price Variance (PPV)
